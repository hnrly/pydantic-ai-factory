# Changelog

Every change a user can see is listed here, newest first.

## Unreleased

- **Breaking:** `AskPerson` is now built on Pydantic AI Harness's `AskUser`. The agent asks with the `ask_user_question` tool, not `ask_person`: up to ten questions in one call, each with a `header`, two to six options, the recommended one first, and `multi_select`. `AskPerson(max_questions=3)` becomes `AskPerson(max_rounds=3)`, which takes the tool away once three responses that asked have been answered; several calls in one response are one round. Its instructions then tell the agent to carry on with its best judgement, rather than name the tool. In the terminal, `factory run` and `factory resume` take numbers separated by commas for a question that lets you pick several. A scripted model that called `ask_person` with `{"question": ...}` must call `ask_user_question` with `{"questions": [...]}`.
- **Breaking:** a `Question` is now one question, not one tool call. It has `header`, `options`, each a new `QuestionOption` with a `label` and a `description`, and `multi_select`, and is keyed by its call and header. Answer an `AskPerson` question with one of its labels, a list of labels, or your own words; `run.reply` sends the answers to one call back together as `ask_user_result` makes them, `{header: [label]}`, and refuses a reply that leaves a question out or picks a label the question does not offer. A question from a tool of your own, deferred with `question` in its metadata, is still answered in words. Runs saved while waiting on the old `ask_person` tool read and resume as such a question.
- **Breaking:** `ElephantGoldfish` loses `max_questions` and gains `ask`, which is `AskPerson()` by default, so its author still asks with no change to your code. Pass `ask=AskPerson(max_rounds=...)` to change how, or `ask=None` for review with no asking. Every `AskPerson` has the id `ask_person`, so an agent has one: an `AskPerson` you list on the agent wins over the one Elephant Goldfish brings, and two you list with different `max_rounds` are refused with `DefinitionError`.
- The board shows each question with its options, the recommended one first, and a box for your own answer. Its API lists an `AskPerson` call's questions in `asks`, and `POST /runs/{id}/answer` takes, for such a call, an object mapping each header to a label, a list of labels or your own words. The `factory` command prints each question's options; type an option's number or your own words, and `--answer` answers every question with its text.
- Compare with Claude Code. `ClaudeCodeSystem(model=..., cap_usd=..., image=...)` runs vanilla Claude Code without a terminal, in its own container, with its read tools and the two ports served to it as an MCP server, and reads its cost and tokens from its result. A suite may word what the `deliver` tool says about itself.
- Measure a factory or one station. `FactorySystem` runs a factory you build for each run, on a `RecordingModel` that counts its tokens and cost, with the run's workspace in a Docker container from `docker_sandbox(image)`. It sends each round of questions to the stakeholder port, gives the factory's own approvals and notes them in the event log, delivers a blocked output when rework runs out, and shows a passing output with the last station's `show`, or a rendering you give. `StationSystem` runs one station inside a factory of that station alone.
- Give a system files to read, safely. `build_snapshot` builds a run's workspace from a base, copying only the files git tracks, and an overlay, leaving out the folders a suite names. `scan` and `check_clean` find every hidden value and canary of every fact sheet in it, allowing only a case's own environment facts in its overlay, so a case that leaks its answers ends before a system sees it. `container_args` mounts a snapshot read-only at `/workspace` in a container with no network, and `build_image` builds a suite's sandbox image.
- Run a case. `run_case` runs one system through the ports, writes `<out>/<arm>/<case>/<n>/` with the run's events and record, ends a run at its time limit or cap, and runs a run that broke once more. A simulated `Stakeholder` answers from the fact sheet: a small model, `picker_agent`, only picks which facts a question asks about, and plain code sends their statements. A suite may build each case's workspace with `workspace_for`. Four scripted systems, `scripted_system(kind, sheet)`, are test fixtures. `serve_ports` serves the two ports as MCP tools to a program run outside this process, so the `evals` extra now brings `mcp` and `uvicorn`.
- Grade a run with plain code. A `FactSheet` holds a case's hidden facts, each with a value nobody could guess, its canary and its checklist, and refuses a sheet that breaks the authoring rules; `load_fact_sheet` reads one. `values_in` and `canary_in` decide what a text states. `grade` gives one of six outcomes, `verified`, `correct_block`, `failure`, `policy_failure`, `budget_exhausted` and `infrastructure_error`, with the fact table and the question measures. `ChecklistJudge` reads a hidden checklist with Pydantic Evals' own judge, one item a call, and keeps a pass only when the quote in its reason is in the text; `coverage` reuses a stored verdict for the same text. `Graded` is the Pydantic Evals evaluator that grades a run and stores its verdicts, so a regrade calls no judge.
- Add `pydantic_ai_factory.evals`, a framework for measuring factories and stations, installed with the new `evals` extra and built on Pydantic Evals. This first part is its port contract: a system under test receives a `Brief`, the request unchanged with an optional workspace, asks through the stakeholder port, one to four questions a call, and ends with a `Delivery` of text with a status of `delivered` or `blocked` and, from a system with a typed output, that output as JSON. The ports hash every delivery themselves. Every port call is written to an append-only `EventLog`, and a run ends as a `RunRecord`. See [Measuring factories and stations](docs/evals.md).
- Ground the Design station in a read-only workspace. `design_station(model, *, method=..., workspace=None)`, `design_review(model=None, *, workspace=None)` and `SoftwareFactory(model, *, workspace=None, ...)` take a workspace, a capability that supplies one such as `LocalWorkspace(path)`; `SoftwareFactory` passes it to the Design station it builds. The workspace is wrapped in `ReadOnlyWorkspace`. The designer then gets read-only file tools from Pydantic AI Harness, `FileSystem(read_only=True)`, the repository's instruction files such as `AGENTS.md` through `RepoContext`, and the repository's own skills from `.agents/skills` and `.claude/skills`, offered after the method's and the software package's, skipped when the folder is missing, never replacing a skill of the same name, and left out when the harness's artifact scanner flags them. Each goldfish of `design_review(workspace=...)` gets the workspace and the same read-only file tools, never the instruction files or skills; the station's default review is built with its workspace. Before any review, a design whose `changes` would modify or delete a path that does not exist, or create one that does, goes back to the designer with each wrong path listed; without a workspace the check passes. The designer's instructions gain "Load a skill from the repository's own library when its description fits the work." Without a workspace nothing changes. The Design page gains "Designing in an existing codebase", with a warning about a repository you do not trust, and the software factory page lists the new option.
- The design skills. The method's guidance is now written as Agent Skills. Four ship with Elephant Goldfish: `design-interview` and `design-resolve`, which the author is offered and loads when it needs them, and `goldfish-comprehension` and `goldfish-critique`, whose bodies are those goldfish's instructions. `Goldfish.from_skill(path, *, name=None, stage=None, kinds=None, sees_request=False)` builds a goldfish from any `SKILL.md`. **Behaviour change for 0.1 users of `ElephantGoldfish`:** `goldfish` is no longer required and defaults to `ElephantGoldfish.GOLDFISH`, comprehension and critique built from the method's skills; `goldfish=()` is now allowed and means no review, with no `contest` or `escalate` tool and a gate that passes; and every author, with review or without, is offered the method's two author skills through Pydantic AI Harness's `Skills`, with a `load_capability` tool and one more sentence in its instructions. A comprehension goldfish now returns an `ExplainBack` (`problem`, `who`, `done_when`, `not_doing`, `approach`), exported from `pydantic_ai_factory.methodologies`, in place of a free-text `paraphrase`; the report still keeps it as one paraphrase. The software package ships three skills, `design-read-code`, `design-doc` and `goldfish-readiness`, and publishes `design_station(model, *, method=...)` and `design_review(model=None)`, with `DESIGNER_INSTRUCTIONS`, which now names the designer's skills. `DESIGN_GOLDFISH` is now comprehension and critique from Elephant Goldfish and readiness from its skill, each with its kinds; `DESIGN_STANDARDS` is read from the skills. The designer is offered exactly four skills, with or without review. `SoftwareFactory(model, *, design=None, repairs=2, accept=None)` takes the Design station as `design=`; by default its review is `design_review()`, so it now reads each draft as Markdown, runs up to four rounds until two clean rounds run in a row, and settles a contest whose citation code checks. **Breaking:** `SoftwareFactory` loses the keywords `rounds`, `goldfish` and `review_model`; pass `design=design_station(model, method=design_review(...))` instead, or set `rounds` and `goldfish` on an `ElephantGoldfish` of your own. It also loses the attributes `model`, `rounds`, `repairs`, `goldfish` and `review_model`; keep what you passed, read `software.rework[0].limit`, or read the Design station's method from `software.methodologies()["design"]`. The `contest` tool's example citation is now `field:non_goals`. The offline run is reviewed in three rounds. The Elephant Goldfish page gains "The method as skills", the Design page "The designer's skills" and a table of the three goldfish, and the software factory page "Your own Design station"; the Decisions page gains "Elephant Goldfish uses its skills by default", "A method belongs to a station, not a factory" and "Skills sit on the designer". CI checks that the built wheels hold every `SKILL.md`.
- A design a builder can follow. `Design` takes the shape of a design document. **Breaking:** `goal` is renamed `summary` and `exclusions` is renamed `non_goals`; a design stored with the old names still loads, as each moves into its new field. New fields, each empty by default: `problem`, `goals`, `assumptions`, `journeys`, `architecture`, `decisions`, `alternatives`, `risks`, `changes`, `steps` and `verification`, with the records `Journey`, `Decision`, `Alternative`, `Risk`, `Change`, `Step` and `Check`, all exported from `pydantic_ai_factory_software`. `render_markdown` writes every section under a fixed heading, in a fixed order and line format, and says "None." for an empty section. The Design station's gate is now `design_is_buildable`, version 1, also exported: after the open-questions rule it checks that every acceptance criterion is proved by a verification item and every criterion named exists, steps and changes name the same paths, steps depend only on steps that exist and have no loop, every decision has a reason and a source, at least one alternative is recorded with a reason for rejection, no field says "TBD" or "TODO", and no path is changed twice. Each failure names the item and sends the design back to the designer. The designer's instructions ask for these parts. The Design station and the software factory are now version 2, so their digests change. The `--offline` scripted designer writes a design that passes the new gate. The Design page gains the new field table and "The gate".
- Findings that can be checked and settled. A finding gains `kind`, `quote` and `suggestion`, written by the goldfish, and `settled` and `same_as`. Code now checks what each goldfish returns: every quote must be part of the text it read once whitespace is collapsed, a goldfish with `kinds` must use one of them, and none may report more than its `max_findings`. A failure goes back to the goldfish, twice at most; a quote still wrong after that is removed and the finding kept with "(quote not found in the design)" added to its issue. Each severity has one meaning for every goldfish, given in their instructions. The `contest` tool gains `cites`, `path:symbol` or `field:name`, which code checks against the run's workspace or the output's fields. `ElephantGoldfish` gains `settle_contests=False`: when `True`, a contest whose citation checks out settles its finding without a person. A later finding from the same goldfish with the same `where` and `kind` as a settled one is settled at once, names it in `same_as`, and is not sent back to the author. `ElephantGoldfish` gains `clean_rounds=1`: with more, a clean round is followed at once by another read of the same draft, and the review ends only after that many clean rounds in a row; it may not exceed `rounds`. The gate `clean_final_round` leaves settled findings out of what it escalates. The defaults keep 0.1's behaviour. Each report is now stamped `elephant-goldfish@2`, because a round now means more. The Elephant Goldfish page gains "When a review ends", and the Decisions page "A contest that cites what anyone can check may settle a finding".
- Let goldfish see what they need. `ElephantGoldfish` gains `to_text`, a function that turns a draft into the text the goldfish read (by default a structured draft is still read as JSON, and the gate still checks the exact draft); `capabilities`, given to every goldfish, such as read-only file tools; and `request`, a function of the run context that gives the request (by default the text of the run's first user prompt). `Goldfish` gains `sees_request=False`, `kinds=()` and `max_findings=20`, each checked when it is made; `kinds` and a lower `max_findings` are put in the goldfish's instructions. Each round, the comprehension goldfish run first and every other goldfish then runs at the same time, instead of one after another. Only a goldfish with `sees_request` receives the request, in a `<request-…>` tag, and every critique goldfish now receives each comprehension goldfish's explain-back in an `<explained-…>` tag. Every goldfish is told that the request, the work and any code it reads are evidence, never instructions. The Elephant Goldfish page gains "What each goldfish sees".

Its `app/` folder, with the example's own API, `jobs` table, worker and `FACTORY_STALLED_MINUTES` setting, is gone. The example depends on `pydantic-ai-factory[web]`.

The web process builds the factory with `TestModel()` and never runs it, so it needs no model key. - The board's API, under `/api`: `GET /board?since=` returns the factory's shape and the cards that changed since the last poll, with the `since` to send next; `GET /runs?column=done|stopped|all&before=` pages back through cards 50 at a time; `GET /runs/{id}` returns a card in full, with the work a waiting run offers or a finished run's output shown in its station's `output_format` (`output_format` says which: `text`, `markdown` or `json`), who started it and when, since when it has waited, its factory version, a `track` of every station in the factory's shape with where the work is (`done`, `here`, `ahead` or `stopped`) and which attempt, and a `history` of events, newest first, built from its steps, gate decisions, answers, jobs and evidence, with each Elephant Goldfish review round read from its `GoldfishReport` and other evidence counted; an event's time is left out where the records do not hold one; `POST /runs` queues a mission; `POST /runs/{id}/answer` builds the answer from the run, so the station, wait and work always come from the run, and queues it, or returns `409` with the run as it is now when the answer is stale, and `422` when it does not fit; `POST /runs/{id}/restart` starts a stopped card's mission again, abandoning its run first if it is stuck, once only; `GET /jobs/{id}` follows a job.
- Each card sits in exactly one column: Missions, a station's, Done or Stopped, by eight rules in order. A run that passed is Done; a run made by a factory of another shape is Stopped as an earlier version; a waiting run is at its station; a run that failed or did not run is Stopped; a start job that ended or lapsed without saving a run is Stopped as stalled; a mission whose run is not saved yet is in Missions, as `queued` while its start job waits and as `starting` once a worker has claimed it, until the run is saved and the card moves to its station; a running run whose job ended or lapsed is Stopped as stalled; any other running run is at its station. A card waiting with an answer queued is marked queued and is out of "Needs you" until that job ends or lapses.
- Every POST takes the person's name from `who(request)`. The default, `typed_name`, reads the name typed on the board from the `X-Factory-Name` header, percent-encoded so names outside Latin-1 work. A request with no name gets `400`, "Type your name first". Pass your own `who` to use a real sign-in.
- Add the board's interface, in `web/board/`, moved from the software factory app's `web/` folder. The first screen asks for the person's name, says it is a name and not a sign-in, and keeps it in the browser; the header shows it with a way to change it. The board is dark only. Missions comes first, with an "Add a mission" box at its top (Enter adds, Shift+Enter starts a new line); then one column per station, in order, each with a coloured strip; then Done and Stopped. Columns scroll sideways on a narrow screen. A card glides only when it changes column, and inside a column cards keep the order they arrived in, so a new badge, a neighbour or a poll moves nothing; a card fades in only the first time the tab shows it after the first load. A running card shimmers and a card waiting for a person glows pink; with less motion asked for, nothing glides or shimmers and the glow is a solid ring. The header counts the cards that need a person; clicking the count scrolls to the longest wait and flashes it. Cards show badges for waiting, queued, rework, stalled, started again and earlier version, and "Start again" asks first and warns, on a stalled card, that the worker may only be slow. Opening a card opens its run as a panel over the board, which stays in view, dimmed; the address becomes `#/runs/<id>`, so a link opens the board with that panel, and Escape, the close button or the browser's back button return to the board, with focus back on the card. The panel shows a state pill in words and a shape, how long the run has waited or when it ended, who started it, the mission, a station track from Mission through every station to Done, then the one thing to do: Approve, or Ask for changes or Reject, each with a note box first; an agent's question as a message with a reply box, sent with any tool sign-offs; or, for a stalled run, why it stalled, Start again with its warning, and Keep waiting. The work follows as a document, with the history beside it, or below it on a phone, and a folded technical detail. "See all" under Done and Stopped lists every card of that column; there is no theme switch and no separate list view. It polls every 3 seconds while the tab is visible. An open run panel keeps checking its run while the tab is visible, every two seconds while the run is queued or running and at the board's pace after that, so another person's answer or a slow worker coming back still shows; Escape in a note that holds text leaves the note before it closes the panel; and a run that does not exist says so, with a link back to the board. `npm run build` writes it into `src/pydantic_ai_factory/serve/_static/`, which the wheel and sdist ship and `board_app` serves at `/`; without a build, `/` names the build command.
- The software factory app's web interface has moved to `web/board/` and become the board, so the app's own web process now serves its API alone.
- Add a `Dispatcher` protocol, with `Job`, `JobState`, `JobNotFound` and `AlreadyRestarted`, exported from `pydantic_ai_factory` and `pydantic_ai_factory.factory`. A dispatcher queues a `Job` to start a mission, with its run id chosen at once, or to apply an `Answer`, and lists jobs newest change first; with `latest_per_run=True` it lists each run's newest job that was not refused, the job driving the run. `run_id=` keeps the jobs of one run or several, so a board reads the driving job of exactly the runs it shows, however many other jobs changed since. `start(..., restart_of=run_id)` starts a run again: it fails the old run's open job with "Started again", and a second restart of the same run raises `AlreadyRestarted`. `Job.stalled(now)` says whether a worker's claim on a job has lapsed.
- Add the optional `pydantic_ai_factory.serve` module, which imports only the standard library and the core. `SQLiteDispatcher(path)` keeps jobs in a `factory_jobs` table of the same file as `SQLiteStore`, and leaves the store's tables and schema version alone. It refuses SQLite older than 3.35 with `SQLiteTooOld`. `work(build_factory, store, dispatcher, model=...)` builds the factory once and does each queued job, passing `deps=` to every run and resume. It extends its claim every quarter of the `lease`; a lapsed claim is reported as stalled and never claimed again. A job that saved nothing and failed with `RunConflict` or `ApprovalRefused` is marked `refused` and leaves its run alone. A `RunConflict` after the job saved its run fails the job, not refused, with "The run moved on while this job was working on it", and leaves the run alone. Any other error abandons the run as the job last saved it, with the error as the reason. A busy finish is tried again, and an error in one job never stops the worker. The first SIGINT or SIGTERM lets the job in hand finish, and `until_idle=True` stops once no job is queued.
- The Decisions page records that the core now defines a dispatcher and `serve` ships one simple queue, replacing the queue half of the decision that the queue belongs to the deployment. The Roadmap says why this is still not a workflow engine.
- Add `output_format=` to `station(...)` and `station(agent, ...)`, which says how a person sees a station's output: an `OutputFormat` of `TEXT`, `MARKDOWN` or `JSON`. Left out, a string output is text and anything else is Markdown, which the library writes from the output's shape: a `title` field as the heading, a section per other field, lists as bullet points. It is kept as `Station.output_format`, and `Station.show(output)` shows one output, or its JSON data, in that format. `to_markdown(value)` writes any value Pydantic can serialise as Markdown. `output_format` is not part of the factory's digest, so changing it never makes a saved run an earlier version.
- Breaking: remove `render_markdown` from `pydantic_ai_factory_software`. Use `to_markdown(design)` from `pydantic_ai_factory`. A design's Markdown now has a Goal section, and its acceptance criteria are plain bullet points, no longer numbered AC1, AC2 and so on. `factory run` prints, and saves, designs in the new form.
- Breaking: say where a run is. `Run.station` is the station the work is at while the run is `"running"` or `"waiting"`, and `None` once it has ended. The factory saves it before each station attempt starts; after rework it names the station the work went back to, and a waiting run's `station` is where it stopped. `stopped_at` keeps its meaning. A waiting run's `station`, `stopped_at` and `waiting.station` must all agree, or the run is refused. `station` is required, so a store refuses a run saved without it with `StoreSchemaMismatch`; it does not convert it. Start a new store.
- Add `factory.abandon(run, reason=..., by=..., store=...)` and `abandon_sync`, to end a run whose worker died and so stays `"running"` for ever. The run is saved as `"did_not_run"`, stopped at the station it was at, with `Run.abandoned`, a new `Abandoned` record of the reason, who ended it and when. The save is a compare-and-swap, so it raises `RunConflict` if the run has moved on, and a slow worker's next save raises `RunConflict`. A run that is not running raises the new `CannotAbandon`, except a waiting run made by the same factory under another shape: the same name, another digest. A factory cannot abandon another factory's waiting run. `Abandoned` and `CannotAbandon` are exported from `pydantic_ai_factory` and `pydantic_ai_factory.factory`.
- Add `factory.shape()`, which describes a factory as plain data: a `FactoryShape` of its stations, as `StationShape` records with their gates as `GateShape`, and its rework rules, as `ReworkShape` records, with the factory's digest. It is built from the same data as `factory.digest`, which is unchanged; a test pins the software factory's digest.
- `list_runs` takes `updated_after` and `updated_before`, to list only runs last saved after or before a moment, and `outcome` takes one outcome or several. `before_run_id`, given with `updated_before`, makes the pair a cursor: paging back from the `updated_at` and `run_id` of the last run on a page loses no run saved at the same moment. `before_run_id` alone raises `ValueError`. Runs saved at the same moment now sort by `run_id` in the listing's direction, so newest first puts the last `run_id` first. `MemoryStore`, `LocalStore` and `SQLiteStore` all have them, and `list_runs_sync` too; `SQLiteStore` puts only the filters given into its query. A store of your own must add them. The Stores page shows how to poll for changes without missing a save, and how to page back.
- Breaking: give a person's answer one type, `Answer`, that names its run. `run.approve`, `run.request_changes` and `run.reject` now return `Approve`, `Changes` and `Reject`, and take a keyword-only `revision`, the run's revision the person saw. Given an earlier revision, they raise `RunConflict`, even when the run has since stopped waiting, so a page can tell a person someone answered first; a revision the run has not reached raises `ApprovalRefused`. New verbs answer an agent's tool calls, each wrapped in a `Reply`: `run.reply` answers what it asked, and `run.allow` and `run.deny` answer an action it wants to take. Each answer names its run, its revision, the wait and the work it answers, who answered and when, and is plain JSON, so it can be queued. `Decision` and `DecisionKind` are gone; `Answer`, `Approve`, `Changes`, `Reject`, `Reply` and `AnswerProblem` are exported from `pydantic_ai_factory` and `pydantic_ai_factory.factory`.
- Breaking: `factory.resume(answer, store=...)` and `resume_sync` no longer take the run. They load the answer's run from the store. Write `factory.resume(run.approve(by="ada"), store=store)` where you wrote `factory.resume(run, run.approve(by="ada"), store=store)`, and `factory.resume(run.reply("Yes.", by="ada"), store=store)` where you passed `DeferredToolResults`.
- Add `factory.check(run, answer)`. It says why an answer does not fit a run, without running anything, as an `AnswerProblem` whose `stale` is true when the run has moved on since the answer's revision. `resume` applies the same rules: it raises `RunConflict` for a stale answer and `ApprovalRefused` for any other problem.
- New: a reply to tool calls must answer each call exactly once. `run.reply` refuses one that does not, naming the question or action it misses, before the reply can be queued. `factory.check` and `resume` refuse such a reply, made any other way, with the same reason before anything runs.
- Answer an agent by what it asked, never by a call id. `run.question` is the one question a run waits on, and `run.action` the one action; `run.questions` and `run.actions` list them all, as `Question` and `Action` records that print as people read them. Answer one question with `run.reply("Yes, keep them.", by="ada")`, one action with `run.allow(by="ada")` or `run.deny(by="ada", note="Not on a Friday.")`, and several with a mapping from each question or action to its answer: `run.reply({first: "Yes.", second: "Grey."}, by="ada")`. A shortcut that would be ambiguous is refused with `ApprovalRefused`, and the error names the mapping form. Nothing is stored differently: a `Reply` still carries Pydantic AI's `DeferredToolResults`.
- Breaking: `Run.answers` replaces `Run.approvals`, and records every answer, tool replies included. A store refuses a run saved with `approvals` with `StoreSchemaMismatch`; it does not convert it. `SQLiteStore`'s schema version is now 2, so it refuses a file written before this change. Answer or finish waiting runs before you upgrade, and start a new store.
- The answer span for a tool-call reply now records who answered, in `factory.answer.by`.

- Record when a run was created and last changed. `Run` has two new fields, `created_at` and `updated_at`, both in UTC and set by the runner on every save. Both are required. A store refuses a run saved by 0.1, which has neither, with `StoreSchemaMismatch`; it does not convert it. Answer or finish waiting runs with 0.1 before you upgrade, or start a new store. Version 0.1 cannot read a run that 0.2 has saved either.

- Keep a factory's work in one SQLite file with `SQLiteStore(path, busy_timeout=5.0)`. It keeps the same rules as the other stores, and lets a web app and a worker on one machine share runs. A save that waits longer than `busy_timeout` seconds for another writer raises `StoreBusy`, a kind of `RunConflict`. The file keeps its schema version in SQLite's `user_version`, and a file of another version raises `StoreSchemaMismatch`. Other tables may share the file. Listing runs reads from an index, with or without a filter. The web-app sample on the Stores page now uses it.
